## 0. Read this first

There is **no live portfolio**. The application is in development.

Two things now exist that did not before, and the distinction matters:

- **The engine** — the application. Phase 07 is in; the folio machinery is
  built and inert at `folio_cohort_threshold = 0.0`.
- **`scripts/swp_dp_model.py`** — a standalone research model, now the
  reference implementation of the withdrawal strategy. It is where the
  mechanisms were worked out, measured, and in several cases found wrong. It
  is NOT the engine and does not share its data model.

`tests/golden/` fixtures are synthetic behavioural pins with different
parameters from the plan. Use them to detect unintended change, never to size
anything.

### How to work

- **One command at a time**, with a gate. Read the output before the next.
  Never pipe to `head`/`tail` in ways that suppress progress; use `tee` when
  both streaming and capture are needed.
- **Patchers**: SHA-256 pin before and after, anchors verified before a byte is
  written, post-hash embedded so the patcher proves its own output. `--check`,
  `--dry-run`, `.bak`, `py_compile` after. `git checkout --` is the recovery
  mechanism. Assert exactly one substitution per hunk.
  **When the payload is a COMPLETE file rather than a diff, accept every
  known-good pre-image** — pinning one cost two round trips in the session of
  31 July because the tree was legitimately a step further along than assumed.
- **Every commit carries a falsifiable claim**, usually "no snapshot moves".
  If one moves, that is a stop, not a judgement call.
- **Predict before running.** A wrong prediction is information; an absent one
  is not.
- `git add` with explicit paths, never `-A`. `.gitignore` is an allowlist whose
  line 2 is `*`; the reliable check that a new file is admitted is `??` in
  `git status --porcelain -uall`.

## 1. The objective

Deliver a fixed annual net cash requirement across two entities — personal and
HUF — at the lowest lifetime tax, and measure what is left at the end.

### The cash identity

```
net cash in hand = W_personal + W_HUF + other income − tax_p − tax_h
```

No transfer term. Tax savings stay in the personal purse; the HUF receives the
inheritance and nothing else. `PLAN_TOL = 1e-2`.

**Check this identity per year, never in aggregate.** A lifetime total can be
right while individual years are wrong in both directions. It caught two
over-delivery bugs that the tax totals hid completely.

### What actually delivers, in order

Revised against measurement. The previous ranking was built before the
standalone model existed and got the second item wrong.

| mechanism | effect | status |
|---|---|---|
| **Anchoring the tax ladder correctly** | removes tax that never existed | model only |
| **The harvest** — realise gain inside the free band and rebuy | the load-bearing mechanism; without it nothing reaches zero at 35 years | model only |
| **Routing the marginal rupee to the cheaper purse** | ~14 of tax at 35 years | model only |
| **Rationing the HUF** across the horizon | large, but the constant is near-optimal already | engine, gated |
| **Scheduling transitions against free capacity** | Phase 07 | **shipped** |
| **Vintage folios** | margin once the harvest exists, decisive without it | engine, inert |

**Folio ordering is deliberately opposite in the two directions.** Harvesting
takes the **dearest** folio — highest front-lot gain fraction, most gain
realised per rupee churned. Cash withdrawal takes the **cheapest**. This was
challenged and re-measured on 31 July; the doctrine is correct.

## 4. What needs to be done

### 4.1 Port the model into the engine — **THE big item, deferred**

The engine's withdrawal strategy should conform to `scripts/swp_dp_model.py`.
This replaces everything the previous document listed as Phases 08, 09, 10 and
the reconciliation gap.

**Deferred pending a prior piece of work, to be specified.**

What the model has that the engine does not:

- debt harvest buying into a **new folio** rather than re-basing in place
- the HUF ration, live rather than gated
- the tiered debt floor
- turnover as a parameter driving the boundary fund groups
- income by head, with s.16(ia) and s.24(a) treatment
- the **equity sleeve under s.112A** — separate tax head, own annual exemption
  per assessee, not eligible for the s.87A rebate, and **harvested** to spend
  an exemption that was otherwise 73% forfeited
- awareness of the **s.87A claw-back's 104% marginal band**
- a per-year marginal-rate split between the purses
- the conservation invariants as tests

**The port is a re-implementation, not a copy.** The model has one NAV per
fund, no exit load on equity, synthetic ladders, and is deterministic. The
engine has real fund data, real dates and real NAVs.

Break it the way the model was built: harvest into a new folio plus the
monotonicity test first, then the floor and the ration, then income heads, then
the equity sleeve. Each with its own falsifiable claim.

### 4.2 `probe_fd_benchmark.py` — rewrite to this specification

Discard the existing implementation and everything the previous document said
about it. The benchmark exists **only** to print a number showing the user how
much tax the strategy saved against holding the money in fixed deposits. It is
illustrative. It does not need to be a portfolio model.

**(a) The FD rate.** Take the family of liquid funds. For each, compute
six-month rolling returns over the last twelve months — six figures per fund.
Across thirty funds that is 180 figures. Average them, express per annum
**without compounding**, then **add 1%**.

> **This cannot be computed from the current codebase.** There is no NAV
> history anywhere: `FundEntry` and the metrics CSV both carry point-in-time
> figures only (`cagr_1/3/5/10`, std dev, sharpe, sortino, calmar, alpha, beta,
> treynor, max drawdown). Six-month rolling returns need a monthly NAV series
> that does not exist. The probe falls back to the mean 1Y CAGR across liquid
> funds plus the 1%, marks it as a fallback, and accepts `--fd-rate` to
> override. **Sourcing a NAV series is a prerequisite for (a) as written.**

**(b) The FD corpus.** **Only money the user contributed from outside, with no
growth of any kind.** That means the opening allocation **plus every external
addition in any horizon year** — ad hoc windfalls and systematic contributions
alike, to either purse. It excludes investment returns, reinvested income and
anything the strategy itself generated.

The FD corpus is a running total of external contributions and nothing else. It
never compounds, is never drawn down, and only ever increases when the user
puts more money in.

**(c) The tax.** Apply the rate from (a) to the corpus from (b) to get each
purse's FD interest. Add that purse's other taxable income. Compute tax with
the **same slab structure and rate schedule used for the horizon**. Sum the two
purses to get `fd_tax_benchmark` per year, and the total across the horizon.

This is deliberately simpler than what exists. Do not reintroduce compounding
or drawdown.

### 4.3 Capital allocator — penalise adjacent-chunk turnover

Add a **heavy penalty when fund overlap between adjacent chunks falls below
67%**, i.e. when turnover exceeds one third.

`find_best_commonality_combination` currently targets a distribution of unique
fund COUNTS across all chunks, globally, as a scoring penalty. Turnover follows
WEIGHT and is a property of each ADJACENT PAIR. The penalty must be on
adjacent-pair weight overlap.

Measurement supports the 67% line. On the model, 3chunk at 35 years:

```
turnover 0.20/0.20   tax  3.434   corpus 2300.7
turnover 0.25/0.25   tax  3.434   corpus 2284.3
turnover 0.33/0.33   tax  4.633   corpus 2177.8
turnover 0.40/0.40   tax 17.050   corpus 2036.1
```

**The cost is steeply non-linear, not proportional.** Going from 33% to 40%
turnover costs four times as much tax, not 20% more. A hard filter at 67%
overlap sits just before the cliff.

Monotonicity is the guard: a tighter threshold shrinks the feasible set, so
turnover can only fall. Carries a fixture regeneration, so it must not be
tangled with another snapshot-moving commit.

### 4.6 Rate-regime stress testing — the practical answer to "no Monte Carlo"

There is no stochastic modelling anywhere in the tax work. Full Monte Carlo
over the strategy is expensive: each 35-year run replays every year up to
`SPILL_GRID × EQ_GRID` times, so a thousand paths is hours, not minutes.

**Do scenario stress testing first, and it is arguably the better instrument
for the risk that actually matters.** The concern is not symmetric noise around
a mean — it is a **directional structural shift from a high-rate to a low-rate
regime**. Monte Carlo around a fixed mean would understate exactly that.

Add a `--rate_path` parameter taking a glide specification, and report tax,
corpus and any shortfall for a small set:

```
flat 7.0%                    the current central case
7.0% -> 5.0% over 10 years   a gradual regime shift
7.0% -> 4.5% over 5 years    a fast one
7.0% -> 4.0% over 15 years   a slow grind
flat 4.5%                    the low-rate world outright
```

Five to ten runs, minutes rather than hours, and it targets the stated risk
directly. Already known from the fixed-rate sweeps: at 4.5% the plan still
funds itself and still ends solvent, but the corpus roughly halves and **tax
falls to zero** — because low returns generate little gain. Tax is a symptom of
success, not of the plan.

Full Monte Carlo, and `EQUITY_SIGMA` with it, remains open after this. It is
the only thing that can price what the debt floor and the equity sleeve are
actually buying, both of which are risk instruments.

### 4.7 Persistent plan cache

Settling a transition plan costs 6–37 seconds per scenario. The in-process
cache is per-worker, so **`pytest -n 8` recomputes the same plan up to eight
times** — the eight workers redo each other's work.

A disk cache keyed on the content fingerprint **plus a hash of the engine
sources**. The source hash is not optional: without it the cache serves plans
built by a previous engine, which is precisely the class of bug that has cost
this project several sessions.

Do after 4.1, which changes the settle cost anyway.

### 4.8 Standing defects

- **`YearSummary.fd_tax_benchmark`** understates 6.2× — a frozen personal-only
  corpus. Reported-only, so correcting it moves ten snapshots and changes no
  behaviour. Subsumed by 4.2's rewrite.
- **A missing debt tax chunk silently yields zero tax.** `compute_slab_tax`
  returns 0.0 when `chunk is None`, which is a reasonable default for most

## 5. The evidence

Findings that cost time to establish. Several contradict what seemed obvious.

### 5.1 The largest single error was a mis-anchored tax ladder

`slab_tax` carried absolute bracket boundaries starting at 4.0 while the
projected basic exemption rose to 10.0. The model charged tax from 4.0
regardless, the projection was cosmetic, and `huf_tax` had a discontinuity —
0.000 at 10.00 and 0.417 at 10.01.

**Much of what the folio and vintage machinery appeared to buy was
compensation for tax that would not have existed.** After the fix the vintage
lever collapsed from a 1.557–19.827 spread to 0.000–0.723.

Check any projected statutory limit against every place that consumes it.

### 5.2 "Draw from the oldest holding first" has now lost three times

It is intuitive and it has been wrong in every measurement. The band is better
spent **harvesting**, which retains units at a stepped-up basis, than on a cash
draw, which removes them. Both extinguish the same gain per rupee of band; only
the harvest improves what is left behind.

Lexicographic widening — maximising the draw from the earliest folio — was the
cause of a long-standing anomaly where one folio outperformed four.

### 5.3 The s.87A claw-back has a 104% marginal band

Between the rebate ceiling and roughly 2.9 above it, marginal relief takes a
rupee of tax for every rupee of income. Above that it falls back to 26–31%.

Consequence: never leave personal income inside that band. Either stay at the
ceiling or jump well past it. A gradient-following optimiser will walk into it
and stop, because from inside it the next step looks cheaper.

Against that, the HUF's first bracket above its own exemption is **5.2%**. The
arbitrage between the two purses is a factor of twenty.

### 5.4 The s.112A exemption is on GAIN, not on cash

Equity LTCG is a separate head: flat rate above an annual exemption, per
assessee, and **not eligible for the s.87A rebate**, so it neither consumes the
debt band nor is sheltered by it. Genuinely additive capacity.

But an exemption of 1.25 frees only about 1.7 of cash when the sleeve's gain
fraction is 72%. **The equity sleeve is a corpus play, not a tax play** — worth
6–13% of terminal corpus from the return premium, and comparatively little tax.

### 5.5 Turnover cost is steeply non-linear

See 4.3. This is the case for constraining overlap at construction rather than
pacing the consequences.

### 5.6 Surplus is concentrated in the first eight years

Every mechanism that depends on fresh money arriving late is inert for this
reason: late vintage cadences, equity bucket rotation, deployment throttling.
Four separate ideas were each defeated by it. Before designing anything that
needs late surplus, check whether any exists.

### 5.7 Single-folio harvesting is worse than not harvesting

It realises gain and shifts the split while the fresh basis sits at the back of
the FIFO queue where withdrawals never reach it. All the cost, none of the
benefit. This is what makes vintage folios load-bearing rather than optional.

### 5.8 The noise floor is about 0.3 on tax

Permuting the fund rotation order — a choice with no economic content — moves a
35-year result across a 0.12 range, and an earlier implementation's apparently
better figure could not be reproduced by any of six random orderings. **Treat
differences below ~0.3 in tax and ~0.1 in corpus as implementation noise.**
Several comparisons that look meaningful in a sweep table sit below it.

## 6. Constraints

- **Legality of the folio split.** CBDT Circular 704 applies FIFO per scheme
  per folio. Several folios across thirty years is unremarkable; the tax
  authorities are not expected to object to four or five.
- **s.64(2).** The HUF's inherited corpus is clean. Resolved favourably;
  re-opens if the personal purse ever transfers into the HUF.
- **The tax treatment is not advice.** s.64(2), Circular 704, GAAR exposure on
  deliberate folio separation, and the HUF's slab treatment all need a CA.

## 7. Gotchas that have already cost hours

- **`--regen-golden` then `git diff` on the snapshot CSVs.** Five sequential
  wrong hypotheses were resolved only by this. Not probes first.
- **Every rupee of surplus must land somewhere.** Two successive versions of
  the model's routing silently discarded the above-floor remainder, vanishing
  685 of corpus and producing a confident, wrong conclusion. The control is one
  line: with the equity sleeve disabled, routing must reproduce the no-equity
  run **exactly**.
- **Instrumentation goes stale when objects are reassigned.** The model
  replaces `personal` and `huf` each year with deep copies, so anything
  captured by patching `Book.__init__` holds a year-one object. This produced
  two wrong readings of the allocation before it was noticed. Measure from
  inside the loop.
- **Dead code is dangerous.** Converting unreachable code gives false
  confidence. Verify call chains before treating a site as a live blocker.
- **Fixtures must exercise the invariant being claimed.** Bugs shipped green
  twice because the fixture never reached the failing path.
- **Predict snapshot movements before looking at the diff.**
- **`re.subn` with lambda replacements**, asserting exactly one substitution.
  A `re.sub` string replacement mangles backslash escapes and reports success
  against the wrong tree.
- **Never angle-bracket placeholders in shell commands** — bash reads them as
  redirection. Quote special characters in commit messages.

## 8. What is not verified

- **The engine has never been run against the model's numbers.** Everything in
  §5 comes from `scripts/swp_dp_model.py`.
- **No Monte Carlo anywhere in the tax modelling.** See 4.6.
- **`EQUITY_SIGMA` is carried and unused.** A deterministic model cannot use a
  standard deviation for anything but false precision.
- **The engine charges no exit load on any live path.** `sell_ordered` and
  `sell_to_tax_budget` apply it correctly and neither has a caller;
  `glide_exit_loads` reads a dict nothing writes; `exit_load_fraction` is in
  `UNUSED_KEYS`. Exit loads measured 0.000000 in every scenario —
  **structurally zero, not coincidentally.** Whether an SWP redemption inside
  `stcg_holding_months` should bear one is an open modelling decision.
- **The withdrawal response is not smooth** and has never been explained. The
  engine has a response floor around 0.01 on a 12–25 L target.
- **3chunk in the model does not hold its allocation.** The transitions are
  one-way emptying mandates; nothing keeps money in the destination funds. Its
  numbers are not comparable to 1chunk and 2chunk.
